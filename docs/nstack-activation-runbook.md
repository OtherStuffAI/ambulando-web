# NStack activation runbook (ambulando-web)

The site stores everything in its own NStack app namespace (see README). For a legacy SQLite migration, close the preservation gates below before activation: replacing the old container discards its ephemeral SQLite. Keep run-specific identities, capture files, hashes, manifests and deployment results in protected, ignored operational evidence.

## Verified facts

- Canonical host: `https://nstack.otherstuff.ai` (service npub `npub1vf3h0rmlrr0x6pjc68jcrk5p2zsfzl3f9zwcppcdn8386npdlxgqmam99v`, build `1d01c72`). `sb4.otherstuff.studio` reports the same service npub on a newer build; the site targets `nstack.otherstuff.ai`.
- Deployed generic contract (commit `1d01c72`): `/api/v4/workspaces/:owner/apps/:app/db/{descriptor,provision,migrations,tables/:t/query,tables/:t/rows[/:id]}`, app-signed (NIP-98 by the registered app npub). `native-v1` is not deployed there (404) and is not used.
- Target: CapRover `secondary` (`captain.b.otherstuff.ai`), app `ambulando-web`, domain `ambulando.io`. The legacy source was version 4, `hasPersistentData:false`, no volumes. Read the current deployment before every mutation; never assume that legacy version remains live.
- Contract tests: `scripts/real-nstack-test.sh` (Tower's real app-db code + throwaway PostgreSQL) and `bun test ./test`.

## Gates (in order)

1. **Resolve the namespace owner and register the existing app identity.** Read the intended workspace from live `/api/v4/flightdeck-pg/workspaces`; use its explicit `workspace_owner_npub`, not its workspace UUID or `workspace_service_npub`. Encrypted-record workspace discovery may return no rows even when typed workspace membership exists. A workspace manager can register directly; an agent can use an active owner-approved `namespace.manage` grant for that exact agent/app (production permission UI supports this). The agent still signs as itself.
   - Check delegated authority/readback with `GET /api/v4/workspaces/<owner npub>/apps?app_npub=<app npub>`. A successful empty list establishes authorized access before registration; it does not establish registration.
   - Register with `POST /api/v4/workspaces/<owner npub>/apps` and `{"app_npub":"<existing app npub>","app_name":"ambulando-web","capabilities":["wapp","app-db"],"enabled":true}`. Read back the exact app, capabilities, enabled state and creator.
   - Decrypt only the existing application's protected custody ciphertext in-process. Use that app signer to provision and install `src/schema.ts`, verify the migration checksum, and exercise insert/read through a fresh client/delete. A new client proves server-backed persistence, not service-restart durability. Keep run-specific identities and results in the ignored handoff.
2. **Capture the live SQLite and encryption key before any source runtime mutation.** Public counts do not establish absence of private records. Use SQLite online backup or read-only `VACUUM INTO` to incorporate committed WAL data, preserve the original `secret.key`, and verify file hashes, integrity, foreign keys and all table counts after protected transfer. Retain originals. Do not restart the source, change its environment or mount over its data directory first.
   - The standard CapRover agent proxy has no container-file capture or command execution route. The existing owner-space app deployment interface supports a separately registered helper with a host-path volume. A one-shot, reviewed helper can use this transport, but Docker socket access is host-root authority and requires explicit review; a read-only socket bind does not restrict Docker operations.
   - Pin the exact service, source container, image/version/digest and start time. Use a fixed capture command with no caller-supplied command/path. Encrypt the artifact before serving it; protect the output endpoint with a memory-held token and TLS. Decrypt the wrapped artifact key through the agent broker, never by exporting the agent key. Keep helper code/custody operational and ignored.
   - Reconcile failed or lost deployment responses against supported deployment history and remote state before retrying. An HTTP gateway failure does not establish nonexecution.
3. **Take the final snapshot under a verified write barrier, then import.** An initial backup does not preserve writes arriving during import. The reviewed migration used a fixed detached SQLite `BEGIN IMMEDIATE` process, fail-fast lock acquisition, a private nonce/PID marker, a bounded expiry and deterministic rollback release. Verify the actual lock from another connection, process/container identity and remaining deadline before capture and immediately before source replacement. Test contention, cancellation and expiry first.
   - Drain or reconcile in-flight external payments. The empty legacy source allowed a stricter gate: refuse cutover if any accounts, sessions, enrolments, Stripe events or payment configuration appear under the lock. This shortcut is unsuitable for a populated payment system.
   - Run `scripts/import-sqlite.ts` dry-run and import against the final protected source/key; retain both manifests. Verify IDs, backups, settings, derived seats, table counts and canonical hashes through NStack readback. Expired sessions and short-lived authentication challenges are deliberately excluded and must be reported.
4. **Replace the locked source with a no-write maintenance image before environment changes.** An environment merge can replace the old container and release its lock while the old SQLite image is still publicly routable. Avoid that gap: use an exact-app image-only deployment with just `caproverName` and `caproverTarget`, omitting all configuration fields. Verify the deployed handler does not inject defaults that trigger a configuration update before image replacement. The maintenance image must return 503 on every HTTP method/path and have a successful container healthcheck to avoid rollback to the old image. Verify stable maintenance responses on both domains and API routes.
5. **Provision runtime secrets while maintenance is active** through `PATCH /api/owners/:owner/apps/:appId/caprover/environment`. Resolve the local app actually linked to the deployed site. Pin app, secondary target, expected server and domain. Supply `NSTACK_URL`, `NSTACK_APP_NSEC`, `NSTACK_APP_NPUB`, `NSTACK_OWNER_NPUB`, `APP_SECRET_KEY` and `BASE_URL`; preserve unrelated existing environment values. Decrypt credentials only inside the sending process, and preserve the sealing passphrase in encrypted custody. Values are never returned.
6. **Deploy and verify**: push tested `main`, fast-forward and push `deployed`, activate the exact secondary app from the intended committed release, then return to `main`. Check health, public/account/admin routes and assets. The old and new code both report `artifactVersion:v7`, so health alone is insufficient: verify the actual CapRover version/source and a website action persisted in the exact NStack namespace through a fresh client. Remove only records owned by a disposable validation identity. Report browser owner-signing and real Stripe checkout separately if untested.
7. **Remove helper host access and credentials.** The existing owner-space deployment parser forwards explicit `volumes:[]` and `envVars:[]`. Redeploy only the helper as an inert image with these empty arrays and verify remote mounts plus a nonsecret runtime presence check. This leaves an inert service when delete/scale-zero is unavailable; report its cleanup owner rather than claiming deletion. Never apply helper cleanup configuration to the website.

## Recovery

- NStack data is the source of truth. `--rollback <manifest>` removes only rows an import run created.
- The original SQLite file and its manifest are kept untouched; the import can be re-run.
- After replacing the legacy container, use the maintenance image as a safe fallback while repairing NStack activation. Do not reactivate version 4: it would create a fresh empty SQLite. Recovery of legacy data requires the protected captured files and original encryption key.
- Losing `APP_SECRET_KEY` makes saved Stripe keys unreadable (re-enter them in `/admin`). Losing `NSTACK_APP_NSEC` loses write access to the namespace, so keep its custody copy.
